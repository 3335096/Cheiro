# Деплой на Railway

Подробный runbook: `docs/ops/railway.md`. Здесь порядок и контрольные точки.

## До деплоя
1. `main` зелёный в CI. Локально `npm run check` проходит.
2. Секреты подготовлены (значения не вставляй в чат и код): `ADMIN_API_TOKEN` (24+ символа), `TELEGRAM_BOT_TOKEN`, `OPENROUTER_API_KEY`, при необходимости ключи OCR.
3. `DEBUG=false`: приложение откажется стартовать с небезопасным токеном админки или без токена бота (так задумано).

## Сервисы в проекте Railway
- `postgres` (с расширением pgvector), `redis`
- `api` (Dockerfile `backend`), `worker` (тот же образ, команда `arq app.worker.WorkerSettings`)
- `frontend` (Mini App), `admin` (админка)

## После деплоя проверь
1. `GET /health` у api возвращает `ok`.
2. Воркер в логах: подключился к Redis и БД.
3. В админке загружается книга и доходит до `ready`.
4. Бот открывает Mini App по HTTPS-адресу фронтенда; проходит сценарий «фото → статусы → тизер → полный отчёт в боте».
5. Фото не остаются нигде (проверь, что в логах нет изображений и base64).
6. Откат: в Railway откати деплой на предыдущий; миграции БД назад только если они обратимы.

Сам деплой, секреты и изменение продакшена делает владелец; агент готовит чек-лист, конфигурацию и проверки.
